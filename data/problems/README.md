# VERNIQ Problem Catalog Dataset Architecture

> **Document Version:** 1.0.0  
> **Status:** Production Standard (Phase 3.0 Foundation)  
> **Scope:** Problem Catalog Ingestion, Preservation, Validation & Pipeline Staging

---

## 1. Directory Structure & Lifecycle Purpose

The `data/problems/` directory serves as the isolated, deterministic repository location for all problem catalog data ingestion.

```
data/
└── problems/
    ├── raw/          # Pristine, byte-for-byte original source files
    ├── staging/      # Non-destructive validated snapshots ready for pipeline processing
    ├── processed/    # Normalized, taxonomy-mapped datasets generated by the pipeline
    └── README.md     # Governance, contract specification, and pipeline documentation
```

### 1.1 `raw/`
- **Purpose**: Stores original source files exactly as provided from external sources or contributors.
- **Preservation Rule (Mandatory)**: Files in `raw/` are **immutable**. They must NEVER be edited, reformatted, modified in-place, cleaned, or partially overwritten.
- **Integrity**: Every file introduced into `raw/` must have its SHA-256 checksum, exact byte count, and source provenance recorded.

### 1.2 `staging/`
- **Purpose**: Holds non-destructive, validated copies or partitions of datasets that have passed schema and format verification.
- **Rule**: Staging files are read-only intermediates. No destructive transformations or lossy truncations are permitted here.

### 1.3 `processed/`
- **Purpose**: Houses the deterministic outputs generated by downstream normalization, slug generation, taxonomy mapping, and seed compilation in Phase 3.1+.
- **Rule**: All files in `processed/` must be 100% reproducible from `raw/` through executable pipeline scripts. They are never authored manually.

---

## 2. Raw-Data Preservation Rule

1. **Byte-for-Byte Immutability**:
   Once placed in `data/problems/raw/`, a source dataset file must not be modified by any script, tool, linter, or developer.
2. **Out-of-Place Transformations**:
   All cleaning, deduplication, enrichment, and normalization operations MUST write their outputs to `data/problems/staging/` or `data/problems/processed/` as distinct artifacts.
3. **Auditability**:
   A corrupted raw file invalidates all downstream artifacts. If a raw file is replaced, it must be registered with a new version identifier or filename timestamp.

## 3. Dataset Contract: Expected Source CSV Format

The raw source CSV file is expected to contain the following columns:

| Column Name | Required | Data Type | Description & Contract Constraints |
|:---|:---:|:---:|:---|
| `Verniq_ID` | **Yes** | String / Integer | Unique problem identifier in the source dataset. Must be non-empty and globally unique within the dataset. |
| `Title` | **Yes** | String | Human-readable problem title. Must be non-empty string. |
| `difficulty` | **Yes** | String | Difficulty rating. Must evaluate case-insensitively to one of: `Easy`, `Medium`, `Hard`. |
| `Topics` | **Yes** | String | Comma-separated list or formatted string of algorithmic topics and tags. Must not be empty or structurally malformed. |
| `companies` | **Yes** | String / Numeric | **Raw source field.** Numeric or string values present in the source dataset. |
| `records` | **Yes** | String / Numeric | **Raw source field.** Numeric or string values present in the source dataset. |

### ⚠️ Critical Semantic Disclaimer for `companies` and `records`
> **DO NOT ASSUME SEMANTIC MEANINGS FOR NUMERIC VALUES.**  
> The numeric or scalar values in `companies` and `records` MUST NOT be assumed to represent company counts, problem IDs, submission counts, or benchmark scores.  
> They are strictly documented and preserved as **raw source attributes** until their definitive provenance and metadata schema are established. Do not rename, re-type, or reinterpret these columns in Phase 3.0.

## 4. End-to-End Problem Catalog Pipeline Workflow

```
   ┌───────────────────────┐
   │    RAW SOURCE CSV     │  (e.g., data/problems/raw/problems_v1.csv)
   └───────────┬───────────┘
               │
               ▼
   ┌───────────────────────┐
   │ 1. Schema Validation  │  (backend/importer/validator.py)
   │    & Integrity Check  │  - Header conformance, quote parsing, type checks
   └───────────┬───────────┘  - Duplicate Verniq_ID & title detection
               │
               ▼
   ┌───────────────────────┐
   │ 2. Pipeline Staging   │  (data/problems/staging/)
   │    & Clean Manifest   │  - Verified clean CSV snapshot
   └───────────┬───────────┘
               │
       [ PHASE 3.1+ FUTURE PIPELINE BOUNDARY ]
               │
               ▼
   ┌───────────────────────┐
   │ 3. Normalization      │  - Title trimming, canonical slug generation
   │    & Slugification    │  - Difficulty casing alignment with PostgreSQL enum
   └───────────┬───────────┘
               │
               ▼
   ┌───────────────────────┐
   │ 4. Taxonomy Mapping   │  - Reconcile `Topics` with `public.tags`
   │                       │  - Reconcile curriculum nodes in `public.topic_problems`
   └───────────┬───────────┘
               │
               ▼
   ┌───────────────────────┐
   │ 5. Database Import    │  - Idempotent upsert via transactional batches
   │    (Supabase/Postgres)│  - Strict referential integrity on `public.problems`
   └───────────┬───────────┘
               │
               ▼
   ┌───────────────────────┐
   │ 6. Verification       │  - Row count parity check, orphan tag checks
   │    & Audit Report     │  - Written to docs/data/import_reports/
   └───────────────────────┘
```

> **Note on Scope**: Normalization, taxonomy mapping, database insertion, and seeding of the 3,392 problem records belong to **Phase 3.1+** and are **NOT executed in Phase 3.0**.

## 5. Validation Rules & Rejection Criteria

The validation engine enforces strict zero-tolerance criteria. **It does not silently fix bad data.** Any violation results in an actionable error report specifying row numbers and field values:

1. **Header Conformance**:
   - The file must contain all required columns: `Verniq_ID`, `Title`, `difficulty`, `Topics`, `companies`, `records`.
   - Extra columns are flagged; missing columns cause immediate rejection.
2. **Format & Encoding**:
   - Must be valid UTF-8 (or ASCII) encoded CSV.
   - Quotation marks and multiline cells must be RFC 4180 compliant without unclosed delimiters.
3. **Non-Null Constraints**:
   - `Verniq_ID` must not be empty or whitespace-only.
   - `Title` must not be empty or whitespace-only.
   - `difficulty` must not be empty.
4. **Uniqueness**:
   - Every `Verniq_ID` must be unique across the entire dataset. Duplicate IDs trigger validation failure.
   - Duplicate `Title` entries are flagged and reported with all corresponding row numbers.
5. **Enum Validity**:
   - `difficulty` must match `Easy`, `Medium`, or `Hard` (case-insensitive). Values such as `Expert`, `None`, `1`, `N/A` are rejected.
6. **Topic Syntax**:
   - `Topics` must contain valid non-empty tokens. Malformed delimiters, unclosed brackets, or unescaped control characters are rejected.

## 6. Naming & Provenance Conventions

- **Raw Files**: `data/problems/raw/problems_source_<YYYYMMDD>_<version>.csv`
  - Example: `problems_source_20261001_v1.csv`
- **Staging Files**: `data/problems/staging/problems_staged_<YYYYMMDD>_<version>.csv`
- **Processed Files**: `data/problems/processed/problems_normalized_<YYYYMMDD>.json` or `.sql`
- **Provenance Log**:
  Every raw ingestion must record:
  - Source origin / author
  - Timestamp of ingestion
  - Exact file size in bytes
  - SHA-256 cryptographic digest
  - Total line count

## 7. Execution CLI Commands

The repository provides a dedicated, dependency-free validation suite:

```bash
# Validate a candidate dataset in raw or staging
python -m backend.importer.cli validate --file data/problems/raw/<filename>.csv

# Generate a detailed validation report
python -m backend.importer.cli report --file data/problems/raw/<filename>.csv

# Run validator unit tests
python -m unittest backend/importer/tests/test_validator.py
```
